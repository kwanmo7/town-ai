## 공통 규칙
- Base URL: `/api`
- 요청 및 응답 형식: `application/json`
- 날짜 형식: `yyyy-MM-dd`
- 날짜·시간 형식: UTC ISO 8601, 초 단위 (`yyyy-MM-dd'T'HH:mm:ss'Z'`)
- `visitDate`는 업무 날짜이므로 시각을 포함하지 않음
- `createdAt`, `updatedAt` 등 시스템 시각에는 정렬·감사·재시도를 위해 시·분·초를 포함하고 밀리초는 사용하지 않음
- ID 타입: `BIGINT`
- 점수 범위: `0` 이상 `10` 이하
- 점수 타입: 정수
- 성공 응답은 공통 Wrapper 없이 리소스를 직접 반환
- 오류 응답은 공통 형식 사용
- Spring Boot Actuator 운영 Endpoint는 `/api` Base URL과 공통 오류 형식을 사용하지 않음
- Web 관리 API는 인증 활성화 환경에서 `Authorization: Bearer {Firebase ID Token}` 필수
- LINE Webhook, Cloud Tasks 내부 Endpoint와 Health Check는 각 용도에 맞는 기존 인증 경계를 유지
- LINE에서 직접 여는 Report 본문·다운로드는 30일 만료 HMAC-SHA256 서명 URL만 허용

## 공통 HTTP Status
| HTTP Status | 사용 기준|
|----|----|
| `200 OK` | 조회 및 수정 성공 |
| `201 Created` | 리소스 생성 성공 |
| `204 No Content` | 삭제 성공 |
| `400 Bad Request` | 요청 형식 오류 또는 Validation 실패 |
| `401 Unauthorized` | Firebase ID Token 또는 LINE 요청 인증 실패 |
| `403 Forbidden` | 인증된 Firebase 사용자가 허용된 관리자가 아님 |
| `410 Gone` | LINE 공개 Report 링크가 만료됨 |
| `404 Not Found` | 요청한 리소스가 존재하지 않음 |
| `405 Method Not Allowed` | 지원하지 않는 HTTP Method 요청 |
| `409 Conflict` | 리소스 상태 또는 데이터 충돌 |
| `500 Internal Server Error` | 서버 내부 오류 |
| `502 Bad Gateway` | 외부 API 호출 실패 |
| `503 Service Unavailable` | 외부 서비스 또는 저장소 일시 사용 불가 |

## 오류 응답

```json
{
  "timestamp": "2026-07-12T14:30:00Z",
  "status":400,
  "code": "VALIDATION_FAILED",
  "message": "요청 값이 올바르지 않습니다.",
  "path": "/api/visits",
  "errors":[
    {
      "field": "atmosphereScore",
      "reason": "0이상 10이하의 값이어야 합니다."
    }
  ]
}
```
- `errors`는 필드 단위 오류가 있는 경우에만 포함
- `code`는 Backend에서 정의한 오류 코드 사용

## 공통 오류 코드

| HTTP Status | code | 사용 기준 |
|----|----|----|
| `400` | `MALFORMED_REQUEST` | JSON 문법 오류, 타입 불일치 등 요청 본문을 읽을 수 없음 |
| `400` | `VALIDATION_FAILED` | 필수 값 누락, 길이·범위·날짜 형식 등 필드 검증 실패 |
| `400` | `INVALID_DATE_RANGE` | 조회 시작일이 종료일보다 늦음 |
| `400` | `INVALID_REPORT_TARGETS` | Report Type에 맞지 않는 `areaIds` 개수, 누락, 중복 또는 불필요한 전달 |
| `400` | `UNSUPPORTED_REPORT_TYPE` | 지원하지 않는 Report Type 요청 |
| `401` | `INVALID_LINE_SIGNATURE` | LINE Webhook 요청 서명 검증 실패 |
| `401` | `INVALID_LINE_TASK_AUTHORIZATION` | LINE 내부 Task 요청 OIDC 인증 실패 |
| `401` | `AUTHENTICATION_REQUIRED` | Web 관리 API에 Firebase ID Token이 전달되지 않음 |
| `401` | `INVALID_FIREBASE_TOKEN` | Firebase ID Token 형식·서명·발급자·만료 검증 실패 |
| `403` | `WEB_ACCESS_DENIED` | 인증 사용자의 UID가 허용된 단일 관리자 UID와 다름 |
| `401` | `INVALID_REPORT_LINK` | LINE 공개 Report 링크의 서명이 없거나 요청 경로와 일치하지 않음 |
| `410` | `REPORT_LINK_EXPIRED` | LINE 공개 Report 링크의 유효 기간이 지남 |
| `404` | `AREA_NOT_FOUND` | Area가 존재하지 않거나 Soft Delete됨 |
| `404` | `VISIT_NOT_FOUND` | Visit이 존재하지 않음 |
| `404` | `REPORT_NOT_FOUND` | Report가 존재하지 않음 |
| `404` | `ENDPOINT_NOT_FOUND` | 요청 URI에 대응하는 API가 존재하지 않음 |
| `405` | `METHOD_NOT_ALLOWED` | 해당 경로에서 지원하지 않는 HTTP Method 요청 |
| `409` | `AREA_ALREADY_EXISTS` | `(prefecture, city, name)`이 동일한 Area가 이미 존재 |
| `409` | `AREA_HAS_NO_VISITS` | AI Report 분석 대상 Area에 Visit이 없음 |
| `409` | `REPORT_HAS_NO_VISITS` | SUMMARY 또는 ALL을 분석할 활성 Visit이 한 건도 없음 |
| `500` | `INTERNAL_SERVER_ERROR` | 별도 처리되지 않은 서버 내부 오류 |
| `502` | `OPENAI_API_ERROR` | OpenAI API 호출 또는 응답 처리 실패 |
| `503` | `STORAGE_ERROR` | Cloud Storage 저장·조회·삭제 실패 |
| `503` | `LINE_EVENT_DISPATCH_ERROR` | LINE 이벤트를 비동기 처리기로 전달하지 못함 |

- Soft Delete된 Area는 외부에서 존재하지 않는 리소스와 동일하게 `AREA_NOT_FOUND`로 처리한다.
- 오류 `message`는 사용자에게 표시할 수 있는 문장으로 작성하고, 내부 예외 메시지나 민감한 정보를 노출하지 않는다.
- 필드 검증 오류가 여러 개이면 `errors` 배열에 가능한 오류를 함께 반환한다.

## Web 인증 API

Firebase Google 로그인 이후 Frontend는 Firebase Client SDK에서 발급받은 ID Token을
관리 API의 Bearer Token으로 전달한다. Backend는 Firebase Admin SDK로 서명, 만료,
발급 Project를 검증한 뒤 `FIREBASE_ALLOWED_UID`와 일치하는 한 사용자만 허용한다.

### 현재 사용자 조회

```http
GET /api/auth/me
Authorization: Bearer {Firebase ID Token}
```

Response

```json
{
  "uid": "firebase-user-uid",
  "email": "owner@example.com",
  "name": "Owner"
}
```

- `WEB_AUTH_ENABLED=true`인 환경에서만 Endpoint가 활성화된다.
- 로그인하지 않은 요청은 `401`, 다른 Firebase UID는 `403`을 반환한다.
- 비밀번호, Google OAuth Access Token 또는 Firebase Refresh Token은 Backend로 전달하지 않는다.


## Area API

### 필드 검증 규칙

| 필드 | 필수 | 규칙 |
|----|----|----|
| `name` | 필수 | 문자열, 최대 25자 |
| `prefecture` | 필수 | 문자열, 최대 20자 |
| `city` | 필수 | 문자열, 최대 20자 |
| `station` | 선택 | 문자열, 최대 50자 |

- `prefecture`, `city`, `name`의 조합은 중복될 수 없다.
- 등록 또는 수정 결과 동일한 조합의 다른 Area가 존재하면 `409 Conflict`와 `AREA_ALREADY_EXISTS`를 반환한다.
- 중복 여부를 판단할 때 `station`은 사용하지 않는다. 하나의 지역에 여러 역이 연결될 수 있기 때문이다.

### 지역 삭제
```http
DELETE /api/areas/{areaId}
```

```http
204 No Content
```

- V1에서는 Area를 물리 삭제하지 않고 Soft Delete한다.
- Soft Delete에는 `deleted_at TIMESTAMP NULL` 컬럼을 사용한다.
- 삭제된 Area는 지역 목록 및 상세 조회에서 노출하지 않는다.
- 삭제된 Area에는 새로운 Visit을 등록하거나 Report 생성 대상으로 지정할 수 없다.
- 기존 Visit은 원본 데이터 보존을 위해 유지한다.
- 삭제되지 않은 Area를 삭제하면 `204 No Content`를 반환한다.
- 이미 삭제된 Area를 다시 삭제하거나 조회 또는 수정하면 `404 Not Found`를 반환한다.
- 복구 API와 보존 기간 이후 Hard Delete 정책은 V2에서 검토한다.


## Visit API

### 필드 검증 규칙

| 필드 | 필수 | 규칙 |
|----|----|----|
| `areaId` | 필수 | 존재하며 삭제되지 않은 Area의 ID |
| `visitDate` | 필수 | `yyyy-MM-dd` 형식 |
| `atmosphereScore` | 필수 | 정수, 0 이상 10 이하 |
| `infraScore` | 필수 | 정수, 0 이상 10 이하 |
| `cleanScore` | 필수 | 정수, 0 이상 10 이하 |
| `sizeScore` | 필수 | 정수, 0 이상 10 이하 |
| `accessScore` | 필수 | 정수, 0 이상 10 이하 |
| `memo` | 선택 | 문자열 |

### 방문 평가 목록 조회
```http
GET /api/visits
```

선택 Query Parameter
```http
GET /api/visits?areaId=1
GET /api/visits?from=2026-07-01&to=2026-07-31
GET /api/visits?areaId=1&from=2026-07-01&to=2026-07-31
```

조회 규칙
- `from`과 `to`는 해당 날짜를 포함한다.
- `from`이 `to`보다 늦으면 `400 Bad Request`를 반환한다.
- 기본 목록과 모든 필터 조회는 Soft Delete되지 않은 Area의 Visit만 반환한다.
- Area를 Soft Delete해도 기존 Visit Row는 이력 보존을 위해 DB에 남지만 일반 Visit 목록에는 노출하지 않는다.
- Visit 목록 필터에서 존재하지 않거나 삭제된 `areaId`를 지정하면 `200 OK`와 빈 배열을 반환한다. 이 규칙은 Area 단건 조회에는 적용하지 않는다.
- 기본 정렬은 `visitDate DESC`, 동일한 방문일은 `id DESC`이다.

```json

  {
    "id": 1,
    "area": {
      "id": 1,
      "name": "센터미나미"
    },
    "visitDate": "2026-07-12",
    "atmosphereScore": 9,
    "infraScore": 9,
    "cleanScore": 10,
```

## Visit Draft API

자연어 입력을 Visit 등록 요청 형태의 초안으로 변환한다. 이 API는 Area나 Visit을 저장하지 않는다. 기존 Area의 `id`가 반환되면 사용자가 확인한 후 `POST /api/visits`로 등록하고, 신규 후보이면 Area 등록 후 반환된 ID로 Visit을 등록한다. LINE 흐름은 확인 시 두 저장을 Backend가 조율한다.

- `text`는 필수이며 빈 문자열은 허용하지 않는다.
- Web은 다섯 점수를 `0`~`10` 정수로 별도 전달할 수 있다. 전달된 점수는 AI가 추출한 값보다 우선한다.
- LINE처럼 점수를 자연어에 포함하는 호출은 점수 필드를 생략할 수 있다.
- OpenAI API 호출 또는 응답 처리에 실패하면 `502 Bad Gateway`와 `OPENAI_API_ERROR`를 반환한다.

### 자연어 방문 평가 파싱
```http
POST /api/visit-drafts
```

Request
```json
{
  "text": "7월 12일 센터미나미에 갔어. 역 앞 광장이 넓고 쇼핑 동선이 편했어.",
  "atmosphereScore": 9,
  "infraScore": 8,
  "cleanScore": 8,
  "sizeScore": 7,
  "accessScore": 7
}
```

Response
```http
200 OK
```
```json
{
  "area": {
    "id": 1,
    "name": "센터미나미",
    "prefecture": "가나가와현",
    "city": "요코하마시",
    "station": "센터미나미역"
  },
  "visitDate": "2026-07-12",
  "atmosphereScore": 9,
  "infraScore": 8,
  "cleanScore": 8,
  "sizeScore": 7,
  "accessScore": 7,
  "memo": "역 앞 광장이 넓고 쇼핑 동선이 편했어.",
  "warnings": []
}
```

- 파싱 결과에는 불확실하거나 누락된 필드가 포함될 수 있다.
- `area.id`가 숫자이면 등록된 활성 Area의 정규 값이며, `null`이면 사용자 확인이 필요한 신규 Area 후보이다.
- 신규 후보는 `name`, `prefecture`, `city`가 모두 있어야 등록할 수 있고 AI가 위치를 보완한 경우 `warnings`로 알린다.
- 신규 후보의 행정구역이 비어 있으면 Backend는 동일 입력으로 위치 보완을 한 번 더 시도한다. 사용자가 도도부현·시구정촌을 직접 입력하지 않아도 지역명이나 역명으로 명확히 특정할 수 있으면 보완하며, 동명 지역처럼 모호한 경우에만 추가 입력을 요구한다.
- 문자열 `"null"`, `"unknown"`, `"광역권"` 같은 자리표시자는 위치 값으로 인정하지 않고 실제 `null`로 정규화한다.
- 실제 Visit 등록 시에는 모든 필수 필드에 기존 Visit API의 검증 규칙을 적용한다.
- 파싱 결과를 Backend에서 재검증하며, AI가 반환한 Area와 점수를 신뢰하여 바로 저장하지 않는다.
- `오늘`, `어제`와 같은 상대 날짜는 `Asia/Tokyo` 기준의 현재 날짜로 해석한다.

## LINE Webhook API

LINE Bot의 메시지 이벤트를 수신하는 Backend Endpoint이다. 일반 사용자용 REST API가 아니며 LINE Platform만 호출한다.

```http
POST /api/line/webhook
X-Line-Signature: {signature}
Content-Type: application/json
```

### 수신 및 전달 규칙

- Backend는 UTF-8로 수신한 가공하지 않은 Request Body와 `LINE_CHANNEL_SECRET`을 사용해 `X-Line-Signature`를 HMAC-SHA256으로 검증한다. JSON 역직렬화는 서명 검증 후 수행한다.
- 서명이 없거나 유효하지 않으면 `401 Unauthorized`와 `INVALID_LINE_SIGNATURE`를 반환하며 이벤트를 처리하지 않는다.
- LINE Developers Console에서 Webhook과 Webhook Redelivery를 활성화한다.
- V1에서는 `LINE_ALLOWED_USER_ID`와 일치하는 1:1 대화의 Follow, 텍스트 Message와 메뉴·Draft·Report Postback Event만 처리한다. Draft의 `edit` Postback은 수정 대기 상태를 먼저 저장하고, 완료 안내를 받은 사용자가 다음 Text Message를 보내도록 한다.
- 허용되지 않은 사용자, 그룹 대화, 텍스트가 아닌 메시지 및 지원하지 않는 이벤트는 외부에 정보를 노출하지 않고 `200 OK`로 종료한다.
- 이벤트가 없는 Webhook URL 검증 요청도 `200 OK`로 응답한다.
- 지원 이벤트는 최소 정보만 `line_webhook_event`에 먼저 저장하고 `webhookEventId` PK로 중복 수신을 방지한다. 원본 Webhook Body, Reply Token 및 Channel Access Token은 저장하지 않는다.
- Webhook 요청 안에서 OpenAI를 호출하지 않는다. DB Commit 후 이벤트마다 Cloud Tasks Task를 생성하고 안전한 전달이 확인된 경우에만 Response Body 없이 `200 OK`를 반환한다.
- Task 이름은 `webhookEventId`로부터 결정적으로 생성한다. 같은 Task가 이미 존재하면 이전 전달이 성공한 것으로 간주한다.
- DB 저장 또는 Task 전달에 실패하면 `503 Service Unavailable`과 `LINE_EVENT_DISPATCH_ERROR`를 반환해 LINE Webhook Redelivery 대상이 되게 한다.

### 비동기 처리 Endpoint

```http
POST /internal/tasks/line-events/{webhookEventId}
Authorization: Bearer {Cloud Tasks OIDC token}
```

- 일반 사용자 및 LINE Platform이 직접 호출하는 API가 아니다.
- Production에서는 Cloud Tasks 전용 Service Account가 발급한 OIDC Token의 서명, Issuer, Audience 및 Service Account를 검증한다.
- Cloud Tasks Header는 처리 정보로만 사용하며 호출자 인증 근거로 신뢰하지 않는다.
- Local에서는 `LocalLineEventDispatcher`, Production에서는 `CloudTasksLineEventDispatcher` 구현을 사용한다.
- 처리기는 `RECEIVED` 이벤트를 `PROCESSING`으로 원자적으로 전환하면서 `attemptCount`를 증가시키고 `processingStartedAt`을 기록한다.
- `COMPLETED` 이벤트가 재전달되면 작업을 반복하지 않고 `2xx`로 종료한다.
- `PROCESSING` 상태가 6분을 초과하면 이전 Process가 종료된 것으로 보고 다음 Cloud Tasks 시도가 이벤트를 다시 점유할 수 있다. 6분 이내의 중복 실행은 `5xx`로 종료해 나중에 재시도하게 한다.
- 일시적인 OpenAI, LINE API 또는 DB 오류가 발생하고 `attemptCount`가 5 미만이면 이벤트를 다시 `RECEIVED`로 전환하고 오류 코드를 기록한 후 `5xx`를 반환해 Cloud Tasks가 재시도하게 한다.
- 다섯 번째 애플리케이션 처리 시도에서도 실패하면, DB를 사용할 수 있는 경우 이벤트를 `FAILED`로 전환하고 마지막 오류 코드를 기록한다. 사용자 안내가 가능하면 실패 안내 Push Message를 Best-effort로 전송한 후 `2xx`로 종료한다.
- Cloud Tasks가 애플리케이션 Endpoint에 도달하지 못해 애플리케이션이 최종 상태를 기록할 수 없는 경우는 Cloud Tasks 최종 실패 로그와 `RECEIVED` 또는 Lease가 만료된 `PROCESSING` Row를 운영 점검 대상으로 관리한다.
- 재시도해도 해결되지 않는 입력 오류는 이벤트를 `FAILED`로 기록하고 사용자 안내가 가능하면 Push Message를 전송한 후 `2xx`로 종료한다.

### 텍스트 메시지 처리

- 텍스트는 `POST /api/visit-drafts`와 동일한 Application Service 및 검증 규칙으로 파싱한다.
- 처리 시작 시 `source_webhook_event_id`로 기존 Draft를 먼저 조회한다. 기존 Draft가 있으면 OpenAI를 다시 호출하거나 INSERT하지 않고 저장된 Draft와 warnings를 재사용한다.
- 파싱 결과는 `line_visit_draft`에 저장하며 생성 시점부터 24시간 동안 유효하다.
- 기존 또는 신규 Area 후보, 위치, 방문일, 다섯 점수 및 memo를 보여주고 누락되거나 모호한 값은 `warnings`로 알린다.
- 필수 값이 모두 유효하면 Draft 상태를 `AWAITING_CONFIRMATION`으로 저장하고 저장·수정·취소 Postback 버튼을 포함한 LINE Push Message를 전송한다.
- 필수 값이 누락되거나 유효하지 않으면 `NEEDS_INPUT`으로 저장하고, 저장 버튼 없이 부족한 값만 자연어로 보완하도록 안내한다.
- 사용자가 수정 또는 보완을 선택하면 Draft를 `AWAITING_REVISION`으로 전환한다. 다음 Text Message는 AI 호출 전에 `revision_webhook_event_id`로 원본을 점유하고 `REVISION_PROCESSING`으로 전환한다.
- Parser는 `changedFields`와 전체 후보 값을 반환한다. Backend는 사용자가 명시한 `changedFields`만 기존 Draft에 병합하고 나머지 값은 모델 출력과 무관하게 유지한다.
- 수정 결과는 새 Text Message의 `webhookEventId`를 사용하는 새 Draft로 저장하고 이전 Draft는 `SUPERSEDED`로 전환한다. 취소·만료·다른 수정으로 점유가 무효가 되면 결과를 신규 Draft로 우회 저장하지 않는다.
- 수정 Text Message가 최초 선택한 원본 Draft ID는 `line_webhook_event.revision_source_draft_id`에 보존한다. 따라서 처리 결과 Push 또는 완료 상태 저장이 실패해 Task가 재시도되어도 수정 입력을 일반 신규 방문 입력으로 다시 해석하지 않는다.
- 비동기 처리에서는 유효 시간이 짧은 Reply Token에 의존하지 않고 `line_user_id`를 대상으로 Push Message를 사용한다.
- Visit 저장이 완료되면 단순 Text 대신 `계속 등록`과 `메인 메뉴` Postback 버튼이 있는 저장 완료 Flex Message를 전송한다.

### Push Message 재시도

- 모든 Push Message는 최초 요청부터 `X-Line-Retry-Key`를 포함한다.
- Retry Key는 고정 Namespace 아래에서 `{webhookEventId}:{messagePurpose}`를 입력으로 사용하는 UUIDv5로 생성한다.
- `messagePurpose`는 `MENU_RESULT`, `REPORT_SELECTION`, `REPORT_GENERATING`, `REPORT_RESULT`, `DRAFT_RESULT`, `CONFIRM_RESULT`, `EDIT_RESULT`, `CANCEL_RESULT`, `FAILURE_NOTICE` 중 하나를 사용해 한 이벤트의 서로 다른 메시지를 구분한다.
- 같은 Retry Key로 재시도할 때 수신자와 메시지 본문을 변경하지 않는다. Draft 결과는 저장된 Draft를 기준으로 동일하게 다시 구성한다.
- LINE API가 `409 Conflict`와 이미 수락된 Request ID를 반환하면 이전 Push가 성공한 것으로 간주한다.
- LINE의 Retry Key 유효 기간 안에서 재시도가 끝나도록 Cloud Tasks 재시도 기간을 24시간 미만으로 제한한다.

### 이벤트 완료 전환

- Draft 또는 Visit 처리 결과를 먼저 DB에 저장한 후 LINE Push Message를 전송한다.
- LINE API가 `2xx`를 반환하거나 이미 수락된 Request ID가 포함된 `409 Conflict`를 반환한 경우에만 `line_webhook_event`를 `COMPLETED`로 전환한다.
- Push 요청이 수락된 후 `COMPLETED` 저장에 실패하면 다음 Cloud Tasks 시도에서 저장된 Draft 또는 Visit 결과와 동일한 Retry Key를 사용해 같은 Push 요청을 재시도한다.
- Push 요청 전에 이벤트를 `COMPLETED`로 전환하지 않는다.

### 저장, 수정 및 취소 처리

- Postback Data는 `action=confirm&draftId={draftId}`, `action=edit&draftId={draftId}` 또는 `action=cancel&draftId={draftId}` 형식을 사용한다.
- Backend는 Postback을 보낸 LINE User와 Draft의 `line_user_id`가 같은지 확인한다. `draftId`만으로 소유 권한을 인정하지 않는다.
- 확인 시 Draft를 `SELECT ... FOR UPDATE`로 잠그고 상태, 24시간 만료, 기존 Area 상태 또는 신규 위치 필드, 날짜와 점수를 다시 검증한다.
- 신규 후보와 같은 활성 Area가 확인 시점에 이미 있으면 기존 Area를 재사용하고, 없으면 Area를 먼저 생성한다.
- 유효한 Draft 확인에서 신규 Area가 필요하면 복합 Key로 먼저 멱등 생성한다. 이후 Visit 문서 저장과 Draft의 `CONFIRMED` 전환 및 `confirmedVisitId` 저장은 하나의 Firestore Transaction으로 처리한다.
- 이미 확인된 Draft의 확인 이벤트가 재처리되면 기존 `confirmed_visit_id`를 사용해 성공으로 처리하고 Visit을 중복 생성하지 않는다.
- `NEEDS_INPUT`, `AWAITING_REVISION`, `REVISION_PROCESSING`, `SUPERSEDED`, `CANCELLED` 또는 `EXPIRED` 상태는 확인할 수 없다.
- 수정은 `AWAITING_CONFIRMATION` 또는 `NEEDS_INPUT` Draft를 `AWAITING_REVISION`으로 전환하며 반복 요청은 같은 안내를 반환한다.
- 취소는 `AWAITING_CONFIRMATION`, `AWAITING_REVISION` 또는 `REVISION_PROCESSING` Draft를 `CANCELLED`로 전환하며 반복 취소는 성공으로 간주한다. 처리 중이던 수정 결과는 저장하지 않는다.
- 완료 결과는 LINE Push Message로 전송한다.

### 메뉴 및 Report 처리

- 친구 추가와 차단 해제에서 발생한 `FOLLOW` 이벤트는 메인 메뉴 Flex Message를 Push한다.
- Postback은 `action`과 유형별 Key를 파싱하며 중복 Key, 예상하지 않은 Key와 조작된 ID를 거부한다.
- `menu`는 `main`, `visit-register`, `report` 화면 이동을 지원한다.
- `report-type`은 `AREA`, `COMPARE`, `SUMMARY`, `ALL`을 지원한다.
- AREA는 Visit이 존재하는 Area 목록을 표시하고, COMPARE는 2~5개 Area 선택 상태를 Postback Data에 보존한다.
- SUMMARY와 ALL은 유형 선택 후 활성 Visit 존재 여부를 확인하며, AREA와 COMPARE는 대상을 확정한 뒤 다시 확인한다.
- 분석할 Visit이 없으면 생성 중 안내나 AI 호출 없이 방문 기록 등록 안내를 전송한다.
- 분석 가능 여부를 확인한 뒤 현재 Prompt 입력 지문과 같은 Report를 먼저 조회한다. 기존 Report가 있으면 생성 중 안내와 AI·Storage 생성을 생략하고 `기존 리포트` 카드로 원래 생성일과 본문·다운로드 URL을 전송한다.
- 같은 Report가 없을 때만 진행 안내를 Push하고 AI 생성과 Storage 저장을 수행한다.
- 입력 지문은 Report Type, OpenAI 모델, Prompt Version, 대상 Area 순서와 실제 Prompt 입력으로 계산한다. 신규 Area·Visit, Area·Visit 수정·삭제, 비교 대상 변경, 모델 또는 Prompt Version 변경으로 생성 조건이 달라지면 새 Report를 생성한다.
- LINE Report는 `source_webhook_event_id`도 UNIQUE로 저장한다. 결과 Push 실패 후 같은 Task가 재처리되면 입력 변화와 관계없이 해당 Event가 만든 기존 Report를 우선 복원한다.
- 완료 Flex Message는 리포트 보기, Markdown 다운로드, 다른 리포트 조회와 메인 메뉴 이동을 제공한다.

### 보관 및 Logging

- 만료된 미확정 Draft는 조회 또는 확인 시 `EXPIRED`로 전환한다.
- 지원 이벤트가 포함된 새 Webhook을 처리할 때 생성 후 30일이 지난 `line_visit_draft`를 먼저 기회적으로 삭제한다.
- Draft가 참조하지 않는 30일 경과 `COMPLETED`·`FAILED` `line_webhook_event`를 이어서 삭제한다. 복구·점검 대상인 `RECEIVED`·`PROCESSING` 이벤트와 확인된 Visit은 자동 삭제하지 않는다.
- LINE User ID, 메시지 원문, memo, Postback Data 및 Token은 로그에 기록하지 않는다.
- 로그에는 `webhookEventId`, `draftId`, 상태, 오류 코드, 재시도 횟수 및 처리 시간만 기록한다.


## Report API

### 리포트 유형

| 유형 | 역할 | Prompt Version |
|----|----|----|
| `SUMMARY` | SQL로 산출한 전체 통계와 항목별 Top 5를 중심으로 구성하고 AI는 짧은 Comment만 생성 | `summary-v1` |
| `ALL` | 모든 Area와 Visit 데이터를 기반으로 AI가 전체 지역 상세 분석 리포트 생성 | `all-v1` |
| `AREA` | 하나의 Area와 Visit 데이터를 기반으로 AI가 해당 지역을 상세 분석 | `area-v1` |
| `COMPARE` | 선택한 2개 이상 5개 이하의 Area를 AI가 항목별로 비교 분석 | `compare-v1` |

- 자연어 방문 평가 Parser의 현재 Prompt Version은 `visit-parser-v1`을 사용한다. V1은 등록된 Area 매칭, 미등록 Area 후보 추출, 위치 확인 및 기존 Draft 부분 수정을 지원한다.

### 리포트 생성
```http
POST /api/reports
```

#### SUMMARY
```json
{
  "reportType": "SUMMARY"
}
```

#### ALL
```json
{
  "reportType": "ALL"
}
```

#### AREA
```json
{
  "reportType": "AREA",
  "areaIds": [1]
}
```

#### COMPARE
```json
{
  "reportType": "COMPARE",
  "areaIds": [1, 2, 3]
}
```

#### 검증 규칙
- SUMMARY, ALL: `areaIds` 생략. `null` 또는 빈 배열을 포함하여 필드가 전달되면 `400 Bad Request`
- AREA: `areaIds` 정확히 1개
- COMPARE: `areaIds` 2개 이상 5개 이하
- AREA 또는 COMPARE에서 `areaIds`가 누락되거나 `null` 또는 빈 배열이면 `400 Bad Request`
- 중복 ID는 허용하지 않으며 `400 Bad Request`
- 존재하지 않거나 삭제된 지역 ID가 있으면 `404 Not Found`
- AREA·COMPARE의 분석 대상 Area 중 Visit이 없는 지역이 있으면 `409 Conflict`
- SUMMARY·ALL에서 활성 Visit이 한 건도 없으면 `409 Conflict`와 `REPORT_HAS_NO_VISITS`
- ALL은 Visit이 없는 활성 Area도 포함하며 `visitCount: 0`, 평균 점수 `null`, 빈 Visit 목록으로 AI에 전달해 데이터 부족 상태를 명시하게 한다.
- 지원하지 않는 `reportType`이면 `400 Bad Request`

#### 대상 지역 저장 규칙
- Report 생성 시 분석 대상 Area ID를 Firestore Report 문서의 `targetAreaIds` 배열에 저장한다.
- AREA는 1개, COMPARE는 요청 순서대로 2개 이상 5개 이하의 ID를 저장한다.
- ALL은 생성 당시 분석에 포함된 모든 Area ID를 저장한다.
- SUMMARY는 Backend 전체 통계를 기반으로 하므로 빈 배열을 저장한다.
- 배열 순서는 AREA와 COMPARE 요청 순서 및 ALL 생성 당시 정렬 순서를 보존한다.

#### 생성 방식
- V1에서는 동기 방식으로 생성한다.
- REST `POST /api/reports`는 명시적인 생성 API이므로 매 요청마다 새 Report를 생성한다. LINE 조회 흐름만 현재 입력 지문이 같은 기존 Report를 우선 재사용한다.
- OpenAI 호출, Markdown 생성, Cloud Storage 저장 및 Report 메타데이터 저장이 모두 완료된 경우에만 `201 Created`를 반환한다.
- OpenAI API 호출 실패 시 `502 Bad Gateway`를 반환한다.
- Cloud Storage 저장 실패 시 `503 Service Unavailable`을 반환한다.
- 생성 과정이 실패하면 Report 메타데이터를 저장하지 않는다.

#### Report ID 선점 및 실패 처리

객체 경로에 `reportId`가 포함되므로 다음 순서로 생성한다.

```text
요청 및 대상 데이터 검증
→ OpenAI 호출과 최종 Markdown 검증
→ Firestore에서 Report 숫자 ID와 임시 Metadata 저장
→ Report ID로 최종 객체 경로 생성
→ Report Storage에 Markdown 저장
→ targetAreaIds와 storagePath를 포함한 Metadata 확정
```

- `storagePath = null`은 ID 선점 직후의 일시적인 Metadata 상태이며 정상 조회 결과로 사용하지 않는다.
- OpenAI 호출과 Markdown 검증은 Firestore 쓰기 전에 수행한다.
- Report Storage 저장 전에 실패하면 불완전 Metadata를 Best-effort 삭제한다.
- Report Storage 저장에 실패하면 불완전 Metadata를 삭제한다. 예약된 숫자 ID Gap은 정상으로 허용한다.
- Report Storage 저장 후 Firestore 확정에 실패하면 방금 저장한 객체와 불완전 Metadata를 Best-effort로 삭제한다.
- 보상 삭제도 실패하면 객체 경로와 오류를 로그에 남겨 운영 정리 대상으로 관리한다.
- 최종 Firestore Metadata 저장이 완료된 후에만 생성 성공으로 간주한다.

### LINE 공개 리포트 조회·다운로드

Firebase 로그인을 사용할 수 없는 LINE 내부 브라우저는 다음 만료 서명 Endpoint를 사용한다.

```http
GET /api/public/reports/{reportId}/content?expires={epochSeconds}&signature={hmac}
GET /api/public/reports/{reportId}/download?expires={epochSeconds}&signature={hmac}
```

- Backend가 LINE 완료 메시지를 만들 때 30일 유효한 URL을 생성한다.
- 서명 대상은 HTTP Method, 전체 경로, Report ID, 조회·다운로드 동작과 만료 시각이다.
- `signature`는 `REPORT_LINK_SIGNING_SECRET`을 사용한 HMAC-SHA256의 URL-safe Base64 값이다.
- Report ID, 동작 또는 만료 시각을 변경하면 `401 INVALID_REPORT_LINK`를 반환한다.
- 만료된 링크는 `410 REPORT_LINK_EXPIRED`를 반환한다. 사용자는 LINE의 리포트 조회 메뉴에서
  기존 Report를 다시 선택해 새 링크를 받을 수 있다.
- 공개 응답은 `Cache-Control: no-store`, `Referrer-Policy: no-referrer`를 사용한다.
- 원래 관리 Endpoint인 `/api/reports/{id}/content`, `/download`는 Firebase 인증 없이는 접근할 수 없다.

### 리포트 삭제
```http
DELETE /api/reports/{reportId}
```

Response
```http
204 No Content
```

- Report 삭제는 Cloud Storage 객체를 먼저 삭제한 후 Firestore Metadata를 삭제한다.
- 존재하지 않는 Report를 삭제하면 `404 Not Found`와 `REPORT_NOT_FOUND`를 반환한다.
- Cloud Storage 객체가 이미 존재하지 않으면 삭제 성공으로 간주하고 Metadata 삭제를 계속한다.
- Cloud Storage 삭제에 실패하면 Firestore Metadata는 유지하고 `503 Service Unavailable`을 반환한다.
- Cloud Storage 삭제 성공 후 Report 문서를 삭제한다. 대상 Area ID는 같은 문서에 포함되어 별도 관계 삭제가 없다.
- Firestore와 Cloud Storage는 하나의 트랜잭션으로 묶을 수 없으므로 부분 실패 가능성을 로그로 기록하고 운영 복구 대상으로 관리한다.

## Statistics API

### 집계 규칙

- 전체 평균은 삭제되지 않은 Area에 속한 모든 Visit을 같은 비중으로 계산한다.
- 지역별 평균은 해당 Area에 속한 모든 Visit을 같은 비중으로 계산한다.
- Top 5는 각 Area의 지역별 평균을 기준으로 산정한다.
- 평균은 소수점 둘째 자리에서 반올림하여 소수점 첫째 자리까지 반환한다.
- Top 5 대상 데이터가 없으면 빈 배열을 반환한다.
- Top 5는 점수 내림차순으로 정렬하고, 점수가 같으면 `areaId` 오름차순으로 정렬한다.
- Soft Delete된 Area와 해당 Area의 Visit은 전체 통계 및 Top 5에서 제외한다.

## Operations API

애플리케이션 운영 상태 확인을 위한 Spring Boot Actuator Endpoint이다. 사용자 기능 API가 아니며 Health Check 이외의 Actuator Endpoint는 외부에 노출하지 않는다.

### Liveness 조회

```http
GET /actuator/health/liveness
```

- Spring Boot 프로세스의 생존 상태만 확인한다.
- DB, OpenAI API 및 Cloud Storage 상태는 포함하지 않는다.
- 정상 상태는 `200 OK`, 비정상 상태는 `503 Service Unavailable`을 반환한다.

Response

```json
{
  "status": "UP"
}
```

### Readiness 조회

```http
GET /actuator/health/readiness
```

- Backend가 요청을 받을 준비가 되었는지 확인한다.
- Spring Boot Readiness 상태와 DB 연결 상태를 포함한다.
- OpenAI API와 Cloud Storage 상태는 포함하지 않는다.
- 정상 상태는 `200 OK`, 준비되지 않은 상태는 `503 Service Unavailable`을 반환한다.

Response

```json
{
  "status": "UP"
}
```

- 두 Endpoint는 Cloud Run Probe 호출을 위해 인증 없이 접근할 수 있다.
- 응답에는 Component 상세 정보, DB 주소 및 내부 오류 내용을 노출하지 않는다.
